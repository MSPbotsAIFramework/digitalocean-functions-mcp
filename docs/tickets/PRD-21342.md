## Product design

### Goals / Non-goals

Goals:
- Let an Agent-platform AI client, through this connector, manage a DigitalOcean account's Functions **namespaces** (create/list/inspect/delete), their **triggers** (create/list/inspect/update/delete), and their **namespace access keys** (create/list/update/delete).
- Credentials travel only in a per-request header (`X-Digitalocean-Token`, the user's DO Personal Access Token) — never stored, never logged, never shared across requests (platform-wide contract, not a per-ticket feature).
- Every call is logged by the standard MCP gateway logging path (tool name, resource ids touched, status, latency) — this connector does not need bespoke audit logging beyond following the platform's existing tool-call logging convention.

Non-goals (v1):
- Deploying, updating, or invoking the function code itself (packages/actions) via the namespace's own OpenWhisk-compatible endpoint — out of scope; the ticket asks for connector-level management ("manage DigitalOcean Functions" in the generic Conduit sense), not a code-deploy pipeline, and doing so would require a second credential (a namespace access key obtained via this same connector) and a different API host per namespace. Flagged as a possible v2 if a later ticket asks for it.
- Any DigitalOcean resource outside Functions (Droplets, Spaces, Databases, etc.) — not requested, not covered by this repo.
- OAuth or any credential flow beyond a single bearer-style header — DigitalOcean's own API only supports PAT-based bearer auth for this surface, so there is nothing to design here beyond the standard header contract.

### Acceptance criteria AC1..AC19

- AC1: Given a valid `X-Digitalocean-Token`, When the agent calls `digitalocean_list_namespaces`, Then it returns the namespaces DigitalOcean's API returns for that token (id, label, region), including an empty array when there are none.
- AC2: Given `label` and `region`, When the agent calls `digitalocean_create_namespace`, Then the namespace is created and its details are returned; When `region` is omitted, Then the tool returns an `invalid_argument` error without calling DigitalOcean.
- AC3: Given an existing `namespace_id`, When the agent calls `digitalocean_get_namespace`, Then its details are returned.
- AC4: Given an existing `namespace_id`, When the agent calls `digitalocean_delete_namespace`, Then the namespace and its contents are deleted and a confirmation is returned; the tool requires an explicit `namespace_id` — there is no "delete all" or wildcard form.
- AC5: Given an existing `namespace_id`, When the agent calls `digitalocean_list_triggers`, Then the triggers in that namespace are returned, including an empty array when there are none.
- AC6: Given `name`, `function`, `type`, `is_enabled`, `scheduled_details`, When the agent calls `digitalocean_create_trigger`, Then the trigger is created and returned; When a required field is missing, Then the tool returns `invalid_argument` without calling DigitalOcean.
- AC7: Given an existing `namespace_id` + `trigger_name`, When the agent calls `digitalocean_get_trigger`, Then its details are returned.
- AC8: Given an existing trigger, When the agent calls `digitalocean_update_trigger` with one or more updatable fields, Then only those fields are sent upstream and the updated trigger is returned.
- AC9: Given an existing trigger, When the agent calls `digitalocean_delete_trigger`, Then it is deleted and confirmed; the tool requires an explicit `trigger_name` — no wildcard delete.
- AC10: Given an existing `namespace_id`, When the agent calls `digitalocean_list_access_keys`, Then the namespace's access keys are returned, including an empty array when there are none.
- AC11: Given a key configuration, When the agent calls `digitalocean_create_access_key`, Then the key is created and its details (including the one-time key value DigitalOcean returns) are returned to the caller, and the value is never written to logs.
- AC12: Given an existing `key_id`, When the agent calls `digitalocean_update_access_key`, Then the update is applied and the updated key is returned.
- AC13: Given an existing `key_id`, When the agent calls `digitalocean_delete_access_key`, Then it is deleted and confirmed; the tool requires an explicit `key_id` — no wildcard delete.
- AC14: Given a `namespace_id` / `trigger_name` / `key_id` that does not exist, When any get/update/delete tool is called with it, Then the tool returns a structured `not_found` error — never a raw 404 passthrough, never a 500, never a silently empty success.
- AC15: Given a request missing the `X-Digitalocean-Token` header, When any tool is called, Then the response is `401` and its body lists the required header name — never a `500`.
- AC16: Given DigitalOcean's API returns `429` or a `5xx`, When any tool is called, Then the call is retried with bounded backoff (total time under 120s) and, on exhaustion, returns a structured `rate_limited` / `upstream_error` — never an unhandled exception.
- AC17: Given two requests in the same running container carry two different tokens (two different DigitalOcean accounts), When each calls any tool, Then neither ever sees the other's data or reuses the other's derived state — credentials and any derived request state live only in a per-request context, never a module-level/global variable.
- AC18: Given `GET /health` is called with no credential header, When DigitalOcean's API is unreachable or slow, Then `/health` still returns `200 {"status":"ok"}` — it is a local liveness probe, not a dependency check.
- AC19: Given the generated `tools/list`, When inspected, Then every `list_*`/`get_*` tool is marked `readOnlyHint: true` and every `delete_*` tool is marked `destructiveHint: true`.

### Open questions

## Tech design

### Conclusion

Build a brand-new Python 3.12 + `uv` + FastMCP server in `MSPbotsAIFramework/digitalocean-functions-mcp` (currently an empty scaffold), one MCP tool per DigitalOcean Functions REST endpoint (13 tools, 1:1, see Change list), fronted by the SOP's standard per-request header-credential middleware. No existing code to extend — this is 100% new implementation against DigitalOcean's public, unauthenticated-to-read API reference. The only upstream credential is a single bearer-style Personal Access Token, so there is no OAuth or multi-step auth flow to design.

### Key flow / sequence

```
Agent -> Gateway -> digitalocean-functions-mcp: POST /mcp tools/call digitalocean_create_namespace
  middleware: read X-Digitalocean-Token -> contextvar; missing -> 401 (ends here)
  tool: validate required params -> invalid_argument if missing (ends here)
  client: POST https://api.digitalocean.com/v2/functions/namespaces, Authorization: Bearer <token>
    DigitalOcean: 429/5xx -> client retries with backoff (bounded <120s) -> success or rate_limited/upstream_error
    DigitalOcean: 2xx -> map response to tool result
  middleware: contextvar reset (finally) regardless of outcome
Agent <- Gateway <- tool result (success or structured error)
```

### Non-functional

- Idempotency & concurrency: all 13 operations map 1:1 to DigitalOcean's own REST semantics (DigitalOcean owns idempotency for creates/updates); our layer adds no local state, so concurrent calls from different tenants never interact. `digitalocean_update_trigger`/`digitalocean_update_access_key` are not inherently idempotent (PUT semantics depend on DigitalOcean) and are not marked `idempotentHint`.
- Performance: single outbound call per tool invocation except on retry; connect 5s / read 30s timeouts; bounded retry/backoff keeps a single tool call under 120s total, consistent with the SOP's network-robustness requirement. List endpoints are not documented by DigitalOcean as paginated for these three resource groups (see Current state); results are returned as-is, with the platform's generic 20000-char response cap and `has_more` truncation applied defensively in case an account has an unusually large number of namespaces/triggers/keys.
- Security: the only secret is the caller's DigitalOcean PAT, read once per request from `X-Digitalocean-Token`, held only in a request-scoped `contextvars.ContextVar`, never logged, never written to disk, never cached across requests. TLS is used for all upstream calls (DigitalOcean's API is HTTPS-only). `digitalocean_create_access_key`'s response (the one-time key value) is returned to the caller but excluded from our own log lines.
- Multi-tenant isolation: per-request credential handling via `contextvars` (set at request start, reset in `finally`) is the entire isolation mechanism — there is no per-tenant storage to isolate because the service holds no state beyond a single in-flight request (AC17).
- Observability: one log line per tool call — tool name, resource id(s) touched (namespace_id/trigger_name/key_id, never the token or key value), upstream status code, latency, our mapped error code if any.

### Decisions made by DEV01

- Tool scope is 1:1 with DigitalOcean's 13 documented Functions endpoints (namespaces, triggers, namespace access keys) rather than also wrapping the function-code deploy/invoke API (the per-namespace OpenWhisk-compatible host) — why: that second surface needs a different credential (a namespace access key, itself obtained via these tools) and a per-namespace base URL, and the ticket only asks for connector-level management, not a deploy pipeline; alternative considered: build both surfaces now — rejected as scope creep beyond what was asked, and flagged as a clean v2 if ever requested.
- Credential header is a single `X-Digitalocean-Token` (the user's Personal Access Token), turned into `Authorization: Bearer <token>` only when calling DigitalOcean — why: SOP §3.1 mandates `X-<Vendor>-<Credential>` naming and forbids passthrough of a caller's own `Authorization` header; alternative: forward the caller's raw `Authorization` header — rejected, against the SOP.
- No pagination parameters are implemented for list endpoints — why: DigitalOcean's reference for these three resource groups documents no `page`/`per_page` params (unlike, e.g., Droplets); alternative: assume cursor pagination exists — rejected as unsupported by the documented contract; the platform's generic response-size cap still applies defensively.
- Tool granularity stays 1:1 with REST endpoints (no merging list/create/get/update/delete per resource into fewer tools) — why: the three resource types have distinct field sets and no natural single-tool combination, and 13 tools is comfortably under the SOP's 20-tool ceiling; alternative: a combined `digitalocean_namespace` tool with an `action` parameter — rejected, it would hide the real operation name and parameters from the agent (SOP's "tools are capabilities, not API-endpoint mirrors" principle cuts the other way here because the endpoints already are the natural capabilities).
- Deletes take only an explicit resource id (`namespace_id`/`trigger_name`/`key_id`) — why: SOP forbids fuzzy/bulk delete tools; alternative: a convenience "delete all triggers in a namespace" tool — rejected.

### Implementation notes not already in "Decisions made by DEV01" (tech design)

- DigitalOcean's actual JSON envelope for these endpoints (`{"namespace": {...}}` / `{"namespaces": [...]}`, and the equivalent singular/plural wrapper for `trigger`/`key`) was not nailed down by the design (flagged there as the one open "assumed" item, though scoped to the trigger body shape specifically). The client unwraps the documented wrapper key defensively (`payload.get("namespace", payload)`) so that if a real account returns the bare object instead of the wrapped one, the tool still returns something rather than `None`. This only affects response *shape fidelity* against a real account, which is exactly what TC29 (manual, no account available) is for.
- `digitalocean_create_trigger` treats `name`, `function`, and `type` as the required fields for AC6/TC12 ("missing a required field (e.g. type)"); `is_enabled` defaults to `True` and `scheduled_details` is accepted as an opaque `dict` rather than a typed schema, since the design's own open question notes DigitalOcean's reference gives field names, not a full JSON schema for this body. Only this validation list and the trigger tools' parameter types would need revisiting once a real account is available -- nothing else in the implementation depends on the exact shape.
- Added a thin `serialization.dumps()` helper (SOP S2.5: compact JSON, `ensure_ascii=False`, defensive truncation with `has_more` if a response ever exceeds 20,000 characters). Not expected to trigger in practice -- DigitalOcean documents no pagination for these three resource groups -- but implemented so the connector does not silently produce an oversized or invalid response if an account ever has an unusually large number of namespaces/triggers/keys.
- Added one INFO-level log line per upstream call in `client.py` (method, path, outcome, elapsed_ms) to give the connector *some* observability per SOP S6, beyond the bare minimum SOP S10 test files ask for. It deliberately never logs headers, request bodies, or response bodies, which is what TC19 exercises directly (the one-time access-key value is returned to the caller but asserted absent from every captured log record).
- `pytest-asyncio`'s default event-loop-per-test means a module-level shared `httpx.AsyncClient` (kept for connection pooling per SOP S5) would be bound to a dead loop by the second test. Added an autouse fixture (`tests/conftest.py::_fresh_shared_client`) that resets the shared client before/after every test; this is test-only plumbing, not a production code path.
